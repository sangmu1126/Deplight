# 4일 완성 배포 시스템 기획안 (Deployment System 4-Day Delivery Plan)

## 🎯 목표 (Goals)
- GitHub OIDC 인증 및 Terraform CLI 자동화를 활용하여 GitHub에서 AWS로 이어지는 배포 파이프라인을 구축한다.
- CI에서 생성된 아티팩트 태그(Image tag)가 Terraform 및 ECS로 제대로 전달되게 하며, 롤백 및 가시성(모니터링) 인프라를 보장한다.
- AI Code Analyzer(코드 분석기) 워크플로우를 연동하여 Terraform 변수 및 배포 권장 사항을 제공한다.
- 스모크 테스트(Smoke tests), 알림 시스템, 핸드오버용 문서(Runbook)를 제작하여 산출물로 제공한다.

## ⚠️ 제약 사항 (Constraints)
- 전체 일정은 단 4일이며, 팀원은 3~4명으로 구성되어 하루 약 12시간을 집중적으로 할당한다 (일정 버퍼 포함).
- 기술 스택으로 GitHub Actions, Terraform CLI, AWS ECS/CodeDeploy, 그리고 AI Analyzer Lambda를 반드시 사용해야 한다.
- 단기 자격 증명(수명이 짧은 토큰)을 선호하며, 수명이 긴 AWS Access Key를 GitHub에 영구적으로 저장하지 않는다.
- 각 태스크는 의존성과 크리티컬 패스(Critical path)를 고려하여 2~5시간 분량으로 나눈다.
- 네트워크 접근이 제한되어 있으므로, 새로운 외부 툴 도입은 승인이 필요하다.

## 🔌 인터페이스 및 데이터 모델 (Interfaces & Data Models)
- **인증**: `sts:AssumeRoleWithWebIdentity`를 사용하여 GitHub OIDC에서 AWS IAM 역할을 위임받는다.
- **이미지 태그**: `<commit_sha>` 태그가 붙은 Docker 이미지가 ECR에 푸시되며, 이 태그는 Terraform CLI를 실행할 때 변수로 전달된다.
- **AI Code Analyzer**: Lambda가 코드를 분석하여 S3에 `generated/terraform.tfvars.json`을 저장하고 PR 댓글을 남기며, 경우에 따라 `infrastructure/` 폴더 아래에 모듈 기반 뼈대를 자동 생성한다.
- **Terraform 실행**: GitHub Actions에서 환경 변수를 통해 S3 + DynamoDB 기반의 리모트 백엔드(Remote state) 설정을 잡아 CLI로 실행한다.
- **파이프라인 흐름**: 분석 워크플로우 ➡️ CI/CD 워크플로우(빌드/테스트/검사 ➡️ 이미지 푸시 ➡️ Terraform Apply ➡️ CodeDeploy ➡️ 스모크 테스트 ➡️ Slack 및 PR 알림).

## 🚨 크리티컬 패스 및 차단 요인 (Critical Path & Blockers)
- **크리티컬 패스 (핵심 경로):** T-01 → T-02 → T-05 → T-06 → T-11 → T-12 순서로 반드시 앞의 작업이 완료되어야 뒤의 작업이 가능하다.
- **현재 차단 요인 (Blockers):** 없음; 단 AWS 계정 및 환경 경계 설정에 대한 최종 확인 대기 중 (오픈 퀘스천 참조).

## 📋 태스크 보드 (Task Board)

[✓] `T-01` GitHub ➡️ AWS OIDC 신뢰 관계 설정 (Critical Path)  
- 범위: AWS IAM 역할 생성, 신뢰 정책 작성, OIDC 클레임 매핑 (단, 글로벌 IAM 재구축은 제외)
- 의존성: 없음  
- 예상 소요: 3h | 우선순위: 필수(Must) | 리스크: 중간 (클레임 불일치 시 배포가 아예 막힘)  
- 인수 조건: 테스트용 워크플로우가 `aws sts get-caller-identity`를 통해 AWS 임시 자격을 무사히 취득할 것.

[✓] `T-02` GitHub Actions 내 AWS 자격 증명 사용 설정 (Critical Path)  
- 범위: `aws-actions/configure-aws-credentials`를 사용하여 OIDC 역할 부여 (기존에 깃허브에 저장된 키 기반 시크릿 모두 제거)
- 의존성: T-01  
- 예상 소요: 3h | 우선순위: 필수(Must) | 리스크: 중간 (설정 오류 시 리소스 적용 실패)  
- 인수 조건: 에러 없이 임시 자격을 얻어 ECS 클러스터 목록을 조회하는 데 성공할 것.

[ ] `T-03` `infrastructure/` 폴더 내 Terraform 모듈 뼈대 스캐폴딩  
- 범위: 베이스라인 모듈 생성 (Network, ECS, CodeDeploy 훅 등). (운영 외의 개발/스테이징 환경 분리 구축은 제외)
- 의존성: 없음  
- 예상 소요: 4h | 우선순위: 필수(Must) | 리스크: 중간 (모듈 인터페이스가 계속 바뀌면 뒷단 작업이 지연됨)  
- 인수 조건: 로컬에서 모듈이 lint/plan에 통과하고, 입력(Input)/출력(Output) 문서가 제공될 것.

[ ] `T-04` Terraform 원격 백엔드 및 CI 파이프라인 연동 설정  
- 범위: S3 + DynamoDB를 이용한 상태(State) 원격 저장, 백엔드 구성, CI 내 보안 변수 처리
- 의존성: T-03  
- 예상 소요: 3h | 우선순위: 필수(Must) | 리스크: 중간 (상태 파일 동기화 실패 시 적용 차단됨)  
- 인수 조건: 합의된 S3 버킷 및 락(Locking) 테이블을 바라보고 CI 환경에서 `terraform init`이 성공할 것.

[ ] `T-05` CI/CD 워크플로우 기본 뼈대 구현 (Critical Path)  
- 범위: 빌드/테스트/SCA 잡(Job) 구성, ECR 푸시, Terraform plan/apply 단계 구성 (단, 언어별 복잡한 단위 테스트 설정은 제외)
- 의존성: T-02, T-03  
- 예상 소요: 4h | 우선순위: 필수(Must) | 리스크: 높음 (전체 배포 오케스트레이션을 담당하므로 가장 중요)  
- 인수 조건: 샘플 브랜치에서 수동 승인 단계를 포함하여 빌드 및 Plan 단계가 정상 완료될 것.

[ ] `T-06` 이미지 태그를 Terraform Apply 단계로 전달 (Critical Path)  
- 범위: 커밋 SHA를 추출해 `-var=image_tag` 형태로 Terraform CLI에 넘기고, ECS에 해당 이미지가 업데이트되도록 설정
- 의존성: T-05  
- 예상 소요: 3h | 우선순위: 필수(Must) | 리스크: 중간 (태그가 잘못 넘어가면 옛날 버전이 배포됨)  
- 인수 조건: Apply 실행 후 ECS 작업 정의(Task definition)가 전달한 `image_tag`로 정상 업데이트될 것.

[ ] `T-07` AI 분석기 워크플로우 호출 기능 연동  
- 범위: 람다(Lambda) 호출, PR에 댓글 달기, S3에서 tfvars 변수 파일 가져오기
- 의존성: T-05  
- 예상 소요: 4h | 우선순위: 권장(Should) | 리스크: 중간 (IAM 권한 및 타임아웃 문제 발생 가능)  
- 인수 조건: 분석기 워크플로우가 분석을 마치고 PR에 권장 사항 댓글을 남기며 산출물 경로를 로깅할 것.

[ ] `T-08` AI 분석 결과를 Terraform 파이프라인에서 소비  
- 범위: `generated/terraform.tfvars.json` 파일 읽어오기, 자동 병합 전 검토 기능
- 의존성: T-07, T-04  
- 예상 소요: 3h | 우선순위: 권장(Should) | 리스크: 중간 (오래된 tfvars가 새 인프라 배포를 망칠 수 있음)  
- 인수 조건: Terraform이 AI가 만들어준 변수 파일을 정상적으로 읽어들이며, 인프라 변경 폭이 클 경우 수동 승인 절차를 밟을 것.

[ ] `T-09` Terraform을 통한 가시성(Observability) 스택 프로비저닝  
- 범위: CloudWatch 대시보드, 경보(Alarms), 로그 보존 기간 설정, X-Ray 설정
- 의존성: T-03  
- 예상 소요: 4h | 우선순위: 권장(Should) | 리스크: 중간 (지표가 없으면 론칭이 지연됨)  
- 인수 조건: Terraform plan 출력 시 대시보드 및 알람 리소스 생성이 표시되며, ARN 값이 문서화될 것.

[ ] `T-10` 자동 롤백 프로세스 확정 및 런북(Runbook) 작성  
- 범위: CodeDeploy 자동 롤백 로직 검증, 수동으로 롤백할 때 필요한 Terraform 명령어 셋 구성
- 의존성: T-06  
- 예상 소요: 3h | 우선순위: 필수(Must) | 리스크: 중간 (롤백 과정이 불분명하면 장애 복구 시간이 길어짐)  
- 인수 조건: 작성된 롤백 매뉴얼을 스테이징에서 직접 테스트하여 CodeDeploy 경보 시 롤백이 작동함을 시연할 것.

[ ] `T-11` 스모크 테스트(Smoke tests) 및 알림 구현 (Critical Path)  
- 범위: 배포 직후 작동 확인을 위한 스크립트 구현, 대시보드 URL이 포함된 Slack 메시지 전송 및 PR 알림 연동
- 의존성: T-06, T-09  
- 예상 소요: 3h | 우선순위: 필수(Must) | 리스크: 중간 (알림이 없으면 배포 실패를 인지하지 못함)  
- 인수 조건: 배포 성공 시 대시보드 링크가 포함된 Slack 알림이 전송되고, 스모크 테스트 실패 시 배포 성공 처리를 막을 것.

[ ] `T-12` 최종 문서화 및 인수인계 (Critical Path)  
- 범위: README 업데이트, 환경 초기 세팅 가이드, 크리덴셜 맵, 완료 조건(DoD) 체크리스트 작성
- 의존성: 이전 모든 태스크 완료  
- 예상 소요: 3h | 우선순위: 필수(Must) | 리스크: 낮음 (문서가 부족하면 후임자가 어려움을 겪음)  
- 인수 조건: README 및 인수인계 문서에 실행 명령어, 환경 변수, 롤백 절차, 테스트 증빙 자료가 전부 포함될 것.

## ✅ 완료 기준 (Definition of Done)
- "필수(Must)" 우선순위를 가진 모든 태스크가 완료되었으며, README/인수인계 문서에 증빙 자료가 링크되어 있어야 한다.
- AI 분석, Docker 빌드, Terraform plan/apply, CodeDeploy 배포, 스모크 테스트 및 알림 전송을 아우르는 전체 CI/CD 파이프라인이 정상적으로 End-to-End 동작해야 한다.
- 롤백 절차가 스테이징 환경에서 시연되고 문서로 정리되어야 한다.
- 가시성(모니터링) 대시보드와 경보가 구축되었으며 접속 URL이 기록되어야 한다.
- 테스트 체크리스트가 전부 수행되었으며 결과가 보관되어야 한다.
- 위험 관리(Risk mitigations) 및 오픈 퀘스천(Open questions)이 완전히 해결되었거나 명시적으로 담당자에게 인계되어야 한다.

## 🧪 테스트 체크리스트 (Test Checklist)

**기능성 (Functional)**
- [ ] OIDC 기반 워크플로우가 `aws sts get-caller-identity`를 성공적으로 로깅한다.
- [ ] CI 작업이 이미지를 정상 빌드/테스트하고 알맞은 태그를 달아 ECR에 푸시한다.
- [ ] Terraform apply 명령이 기대한 `image_tag` 값으로 ECS Task definition을 업데이트한다.
- [ ] CodeDeploy 블루/그린 배포가 구버전에서 신버전으로 정상적으로 트래픽을 넘기고 성공을 보고한다.
- [ ] 스모크 테스트 스크립트가 헬스 체크 엔드포인트를 찔러보고 그 결과를 Slack/PR 댓글로 보고한다.

**비기능성 (Non-Functional)**
- [ ] GitHub 및 람다용 IAM 정책이 '최소 권한의 원칙(Least privilege)'을 준수하여 작성되었다.
- [ ] Terraform 상태 락(State locking) 기능(DynamoDB)이 올바르게 동작하며, 배포 후 인프라 변경(Drift)이 없다.
- [ ] CloudWatch 대시보드가 핵심 메트릭을 렌더링하고 실패 시 알람이 정상 발송된다.
- [ ] 문서화된 롤백 명령어가 정해진 SLA(시간 한도) 내에 실행되어 이전 태그 버전으로 복구시킨다.
- [ ] AI 분석기 람다의 실행 소요 시간과 비용이 합의된 범위 내에 머무는지 기록되었다.
